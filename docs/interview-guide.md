# 学习与面试讲解

## 一分钟项目介绍

FabCopilot 是一个扩散炉良率诊断与维护协同 Agent。我没有让模型直接操作设备，而是把设备数据、报警、知识文档和审批工作流放进可审计的后端。检索使用 PostgreSQL 全文与 pgvector 混合排序，分析使用受限 NL2SQL，Agent 调用这些工具后返回证据轨迹；停机提案必须进入人工审批。系统还加入 Redis、Prometheus、结构化日志、Docker 和 CI，并用真实测试记录指标。

## 为什么这样分层

- 领域规则不能依赖 Web 框架，否则换数据库或测试时成本很高。
- Application 定义 Protocol，相当于“我需要什么能力”；Infrastructure 回答“用什么技术实现”。
- FastAPI 的 Depends 负责把实现组装起来，而不是承载业务逻辑。
- 单测用假的端口实现，集成测试再连真实 PostgreSQL/Redis，兼顾速度与可信度。

## 面试高频追问

### 为什么不用纯向量检索？

设备型号、报警码等精确词适合关键词检索，故障现象的近义表达适合向量检索。两路结果用 RRF 合并，避免手工比较不可比的分数。

### NL2SQL 如何防止删库？

不能只靠提示词。项目在执行前解析 AST，限制语句类型和表，拦截危险函数，强制行数上限；执行时还开启只读事务和超时。这是多层防护。

### 为什么审批结果不能缓存？

审批 ID 是有生命周期的业务状态。如果把含 pending ID 的旧回答缓存并重放，用户可能操作错误的审批单，所以这类结果完全跳过缓存。

### 为什么保留离线模型？

CI 不能依赖密钥、费用和外部网络。确定性规则模型保证工具链和安全状态机可以重复验证；真实模型适配器则通过相同端口替换。

### 当前最大不足是什么？

数据和评测集规模小，embedding 与 NL2SQL 生成器是离线基线，也没有 IAM/RBAC。正确说法是“工程闭环已经建立，模型质量和生产安全能力仍需在真实授权数据上继续验证”，而不是夸大成生产系统。

## 推荐学习顺序

1. 从 `domain/equipment.py` 理解数据类、枚举和不变量。
2. 看 `application/ports` 与 Repository 实现，理解依赖倒置。
3. 跟踪一次 `/agent/diagnose` 请求，画出工具调用时序。
4. 阅读 NL2SQL 校验器，尝试写一个绕过用例并补测试。
5. 查看迁移、Compose 与 CI，理解代码如何变成可运行服务。
6. 最后运行评测和基准，学习如何只使用可复现数字写简历。
